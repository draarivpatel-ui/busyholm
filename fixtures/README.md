# fixtures

Synthetic test data only. Nothing here comes from a real agent session; every payload is built by a script from documented shapes.

## contracts/

`contracts/<contract>/valid/` and `contracts/<contract>/invalid/` hold at least 30 examples each for every contract in `contracts/schemas/`. They are the shared oracle: the TypeScript validator (`npm test`) and the Rust types (`cargo test`) must both accept every valid file and reject every invalid one. `manifest.json` in each folder says what each file covers; for an invalid file it also gives the JSON Pointer of the value that breaks the rule, and the TypeScript test checks that the rejection points there, so a fixture cannot pass by failing for the wrong reason.

Generated by `npm run fixtures:generate` from `tools/fixtures/contracts/<contract>.mjs`. The output is committed; tests never regenerate it. To add a case, edit the module and regenerate.

## agent-inputs/

Raw agent-side inputs as an adapter would see them: Claude Code hook bodies, status line input, registry files and transcript lines; Codex hook bodies, rollout lines and the notify argument; OpenCode plugin events; the Antigravity CLI log; Gemini CLI and Cursor hook bodies. `index.json` lists every file with its agent, source and format.

Every content-bearing field carries a privacy canary (SPEC 5.7 rule 10):
- text fields (prompts, replies, tool inputs and outputs, messages, titles, summaries, error details, emails, branch names) hold a marker `BHCANARY_<agent>_<field>_<n>`, so a leak names its source;
- paths (cwd, transcript paths, file paths) contain a marker as a folder name, and the last segment of every cwd is a marker;
- raw ids (session, thread and agent ids) are UUID-shaped canaries starting `bca1a700-0000-4000-8000-`, so an adapter that checks the UUID shape still accepts them;
- account fields (creator ids, owner ids, emails) hold markers.

`agent-inputs/never-open/` holds stand-ins for files an adapter must never open (credentials, keys, OAuth tokens, `history.jsonl`, `tool-results/`). They are full of canaries, so a file-open spy or a leak in any output proves they were read.

A test (`tools/privacy/test/`) checks that every field named in SPEC 5.7 rule 1, research section 8.4, the account fields and the raw ids carries a canary somewhere in these inputs.

**Project names.** The canary suite runs with the project-name opt-in off. With it on, the last segment of a cwd (a marker) is expected to appear in `Snapshot.agents[].project_label`, and only there; never in the ledger, logs, notifications or exports.

## privacy/

`privacy/canaries.json` lists the needles that `npm run privacy:check -- <dir>` searches for: the text marker prefix and the raw-id prefix (with and without dashes), in every encoding the scanner knows (UTF-8 case-insensitive, UTF-16LE and BE, hex, base64 at all three alignments, URL-safe base64). Compressed or encrypted output is not inspected.

## Using these from other packages

- WP-03 to WP-07: feed `agent-inputs/` through the real adapters, then run `npm run privacy:check -- <output folder>` on everything they write (snapshots, moments, ledger, logs, notifications). Rust tests can call the same scanner, or search for the needles in `privacy/canaries.json` directly.
- Add your own fixtures under a new sub-folder (for example `fixtures/claude/` for WP-04 golden sequences) rather than editing these.
